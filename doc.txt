Here's how your RAG system works end-to-end:

```mermaid
flowchart TD
    A[User uploads PDF] --> B[pdf_reader.py\nPyMuPDF extracts text per page]
    B --> C[chunker.py\nSplit into 500-word overlapping chunks]
    C --> D[ingest.py\nSentenceTransformer encodes each chunk]
    D --> E1[MongoDB\nStores chunk text + metadata]
    D --> E2[FAISS index\nStores float32 vectors on disk]

    F[User asks question] --> G[search.py\nEncode question → float32 vector]
    G --> H[FAISS\nTop-K nearest vector search]
    H --> I[MongoDB\nFetch chunk text by vector_id]
    I --> J[llm.py\nBuild prompt: context + question]
    J --> K[Ollama llama3.2:3b\nGenerate answer]
    K --> L[Streamlit UI\nDisplay answer + retrieved chunks]
```

**Two phases:**

**Ingest** (once per PDF):
1. PyMuPDF extracts raw text page-by-page
2. Each page split into 500-word chunks with 50-word overlap
3. `all-MiniLM-L6-v2` converts each chunk to a 384-dim vector
4. Chunk text + metadata → **MongoDB** (`rag_db.documents`)
5. Vectors → **FAISS** index saved to `indexes/faiss.index`

**Query** (every question):
1. Question encoded to the same 384-dim vector space
2. FAISS does L2 distance search → returns top-5 `vector_id`s
3. Those IDs look up the actual text from **MongoDB**
4. Text chunks assembled as context → sent to **Ollama** with the question
5. LLM answer displayed in **Streamlit**

The key insight: FAISS handles the fast similarity search, MongoDB stores the readable text — they're linked by `vector_id`.

1. MongoDB

Think of MongoDB as a filing cabinet.

Its job is not AI.

It stores:

{
   "_id":101,
   "page":5,
   "text":"Garbage collection improves SSD performance.",
   "embedding":[0.12,-0.34,...]
}

MongoDB stores:

original text
page number
filename
metadata
embedding (optional)

It does not understand the meaning of the text.

It simply stores data.

2. Embedding Model

This is where AI starts.

For example:

Sentence:

SSD firmware validation

becomes

[-0.22,
 0.55,
 0.98,
 ...
 768 values]

This process is called:

Text

↓

Embedding

↓

Vector

The embedding model understands the meaning of text.

Examples:

all-MiniLM
BGE
E5

These are not LLMs.

They are embedding models.

3. FAISS

FAISS is not an AI model.

It is a very fast search engine.

Suppose MongoDB contains

Document A

SSD firmware validation

Vector:

[0.12,
0.45,
0.98]

Document B

Python decorators

Vector

[0.80,
0.22,
0.11]

Now user asks

How to validate SSD firmware?

Embedding model converts it into

[0.11,
0.44,
0.95]

FAISS compares vectors.

Query

↓

Vector

↓

Compare with every vector

↓

Closest vector

↓

Document A

FAISS does nearest-neighbor search.

It does not answer questions.

4. Ollama

This is an LLM.

Examples:

Llama 3
Mistral
Gemma

Ollama simply runs these models on your computer.

Without context:

Question

↓

What is TRIM?

The LLM answers using its general knowledge.

With RAG:

Question

+

Retrieved PDF

↓

LLM

↓

Answer based on your document

Ollama performs reasoning and generates natural language.

5. Why not let the LLM read the whole PDF?

Suppose your PDF has

1000 pages

The LLM cannot efficiently process the entire document every time.

Instead:

1000 pages

↓

Chunk

↓

FAISS

↓

Top 3 chunks

↓

LLM

The LLM receives only the relevant parts.

This makes it:

faster
cheaper
more accurate

Think of it like a library

Imagine a huge library.

MongoDB

The bookshelves.

Stores all books.

Embedding Model

A librarian who understands the meaning of books.

Instead of filing books alphabetically, the librarian groups similar topics together.

FAISS

The library catalog.

You ask:

"I need books about SSD firmware."

FAISS instantly finds the most relevant books.

Ollama

The librarian who reads those books and explains the answer to you in plain English.
